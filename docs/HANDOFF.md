## 0. Как работать с этим документом

Ты агент-разработчик с доступом к GitHub. Этот документ описывает проект целиком. **Прочитай его от начала до конца до первой строчки кода.**

### 0.1 Порядок первых шагов

1. Пользователь создаёт пустой репозиторий (предложенное имя: `nodejs-interactive-textbook`, приватный). Если репозитория ещё нет, попроси пользователя его создать. Не создавай репозитории в чужих аккаунтах без явной просьбы.
2. К документу приложен архив `nodejs-interactive-textbook-scaffold.tar.gz`. В нём уже написанный код (этап 0 и первый урок), история git из трёх коммитов и копии планов в `docs/`. Распакуй его, проверь `npm install && npm test && npm run build`, затем запушь в репозиторий в ветку `main`.
3. Если архива нет, воссоздай каркас по разделам 3–5 и приложению A. Движок event loop и его тесты описаны в 3.3 достаточно подробно для воспроизведения.
4. Выполни **Фазу A** из раздела 13 (укрепление каркаса), прежде чем писать новые уроки.
5. Дальше иди по фазам в порядке раздела 13. Один модуль = одна ветка = один pull request.

### 0.2 Правила работы

- **Достоверность важнее скорости.** Каждый факт о поведении Node.js, PostgreSQL, Redis, Kafka, RabbitMQ, NestJS должен быть либо подтверждён запуском (автотест или лаборатория), либо сверен с официальной документацией. Если подтвердить нельзя, пиши «уточнить» в самом тексте и заноси пункт в `docs/open-questions.md`. Подробнее в разделе 11.
- **Не выдумывай факты о ШЭП, Kalkan, НУЦ РК и других госсистемах.** Для модуля 12 сначала выполняется исследовательский этап (см. 9.13). То, что не найдено в официальных источниках, не описывается как факт.
- **Не придумывай опыт пользователя.** Учебник учит, а не сочиняет биографию. В модуле 14 шаблоны ответов заполняются самим пользователем.
- **Контент хранится данными** (TypeScript-объекты в `src/content`), а не вёрсткой. Компоненты универсальны.
- **Любое изменение семантики движков сопровождается тестами** против реальной системы (Node, PostgreSQL, Redis, брокеры).
- **Не коммить** `node_modules`, `dist`, `dist-single`, секреты, большие бинарники.
- **Язык:** интерфейс, тексты уроков, комментарии к контенту и коммиты на русском. Идентификаторы в коде и имена файлов на английском.
- **Не копируй текст из документации и чужих учебников.** Объясняй своими словами, давай ссылки на первоисточники. Цитаты не длиннее короткой фразы.

### 0.3 Что считать готовым

Определения готовности для урока, модуля и релиза находятся в разделах 11.5 и 12.4. Коротко: урок готов, если проходит `npm run lint:content`, имеет интерактив, блок «как спросят», тест, задачи с режимами 🌐/💻/🔀, проверенные факты и рабочую лабораторию там, где она нужна.

## 2. Принципы продукта

1. **Показывай, а не рассказывай.** Минимум один интерактивный элемент на урок: симулятор, диаграмма или песочница.
2. **Честная граница модели и реальности.** Всё, что в браузере моделирует внешнюю систему, помечено бейджем «модель». Рядом ссылка на локальную проверку на реальной системе.
3. **Режим практики всегда виден:** 🌐 в браузере, 💻 локально, 🔀 гибрид.
4. **Всё привязано к собеседованию.** В каждом уроке есть «как спросят / как ответить», тест на самопроверку и типичные ошибки.
5. **Контент отделён от кода.** Новый урок добавляется данными, без правки компонентов.
6. **Модель проверяется оракулом.** Результат симулятора сверяется с реальной системой автотестами (раздел 11.2).
7. **Работает без сервера.** Основная сборка открывается двойным кликом. Тяжёлые возможности (WASM) подгружаются лениво и имеют запасной путь (раздел 4.3).
8. **Один источник правды.** Сценарии, из которых строится симулятор, генерируют и код для лабораторий, и эталонные ответы.
9. **Доступность.** Клавиатура, `aria-live` для шагов симуляции, контраст, уважение `prefers-reduced-motion`.
10. **Мобильное чтение, десктопная практика.** Тексты и симуляторы удобны на телефоне, локальные задания рассчитаны на компьютер.

### 3.3 Движок event loop: как устроен (для воспроизведения и расширения)

Файл `src/engine/eventloop.ts`. Сценарий описывается деревом операций `Op`:

```ts
type Op =
  | { k: 'log'; text: string }
  | { k: 'timeout'; delay: number; body: Op[] }
  | { k: 'immediate'; body: Op[] }
  | { k: 'nextTick'; body: Op[] }
  | { k: 'promise'; body: Op[] }         // Promise.resolve().then(...)
  | { k: 'chain'; steps: Op[][] }        // Promise.resolve().then(a).then(b)...
  | { k: 'microtask'; body: Op[] }       // queueMicrotask
  | { k: 'io'; body: Op[] }              // fs.readFile(__filename, cb)
  | { k: 'async'; body: Op[] }           // (async () => { ... })()
  | { k: 'await' };
```

Из одного дерева строятся:
- `toSource(ops)`: исходный CommonJS-код для показа и для лаборатории (`.cjs`);
- `simulate(ops)`: `{ frames: Frame[]; log: string[] }`, пошаговая запись выполнения.

**Семантика модели (CommonJS, Node ≥ 11):**
- Основной скрипт выполняется синхронно. После него и после **каждого** колбэка вызывается `drain`: пока очередь `nextTick` не пуста, выполняются её колбэки; затем очищается очередь микрозадач целиком; если за это время появились новые `nextTick`, цикл повторяется.
- Цикл событий: фаза timers (сработавшие таймеры по порядку срока и регистрации; между колбэками `drain`), фаза poll (готовые I/O-колбэки; если делать нечего и есть ожидающие таймеры или I/O, виртуальное время «прыгает» вперёд), фаза check (`setImmediate`; новые immediate, добавленные во время фазы, выполняются на следующем витке).
- Время виртуальное. После основного скрипта `now = 1` мс (моделируем, что прошла ≈1 мс), `setTimeout(d)` готов в `now + max(1, d)`, I/O имеет фиксированную задержку 2 мс.
- Сценарии, где порядок в реальном Node зависит от машины (`setTimeout(0)` против `setImmediate` в основном модуле), помечены `deterministic: false` и не сверяются автотестом. В симуляторе показывается предупреждение.
- Не моделируются: фазы pending и close, `setInterval`, необработанные reject, `await` на «чужих» thenable, `process.nextTick` в ES-модулях (там порядок отличается, это описано в уроке и проверено запуском).

**Тест** (`src/engine/eventloop.test.ts`): для каждого детерминированного сценария генерирует `.cjs`, запускает реальный `node` и требует равенства с `simulate(ops).log`.

Это эталонный образец подхода «модель + оракул», который нужно повторить для остальных симуляторов (раздел 11.2).

| `@axe-core/puppeteer` | автоматическая проверка a11y в e2e | dev-зависимость |

### 4.3 Цели сборки (важное решение)

Нужно три цели, чтобы тяжёлые возможности не ломали открытие «двойным кликом»:

| Цель | Что внутри | Для кого |
|---|---|---|
| `dist/` (папка, `npm run build`) | всё, включая ленивые чанки PGlite и компилятора TypeScript | публикация (GitHub Pages и т.п.) и локальный `vite preview` |
| `dist-single/index.html` (`npm run build:single`) | ядро: оболочка, уроки, симуляторы, JS-песочница. **Без** WASM-тяжёлого | быстрый просмотр без сервера |
| `dist-offline/` (`npm run build:offline`, новая) | как `dist/`, плюс локальные копии всех ленивых ресурсов и `serve.mjs` (запуск `node serve.mjs`) | полностью офлайн-режим для SQL и TypeScript |

В `dist-single` виджеты, которым нужен WASM, показывают заглушку: «Этот виджет требует HTTP-сборки. Запусти `npm run preview` или открой `dist-offline`» и ссылку на инструкцию. Не используй CDN для критичных ресурсов, оффлайн-режим должен работать без сети.

### 4.4 Ограничения и решения

| Ограничение | Решение |
|---|---|
| `file://` блокирует ES-модули и часть Worker-сценариев | одно-файловая сборка; воркеры создаются из Blob (проверено на `file://`) |
| В браузере нет `process.nextTick`, `setImmediate`, `fs` | поведение Node моделируем движками, а настоящий запуск даём в лабораториях |
| PGlite работает с одним соединением | конкурентность (изоляция, дедлоки) показываем сценарной моделью, проверенной оракулом на реальном PostgreSQL в CI; настоящий опыт даёт лаборатория с двумя соединениями |
| Брокеры и NestJS нельзя запустить в браузере | модели плюс лаборатории |
| `localStorage` может быть недоступен или очищен | запасной вариант в памяти, экспорт и импорт прогресса в файл (уже сделано) |

## 5. Архитектура

### 5.1 Слои

```
content (данные)  →  registry (modules.ts, lessons.ts)  →  renderer (Blocks, TaskCard, Quiz, widgets)
                                                                ↓
                                              engine (pure TS, без DOM): модели + тесты
```

Движки (`src/engine/*`) не знают о DOM и тестируются отдельно. Виджеты (`src/components/*`) подключают движок к интерфейсу.

### 5.2 Формат контента

См. приложение A (типы). Урок = массив блоков: `md`, `callout`, `interview`, `widget`, `quiz`, `task`. Новые виджеты регистрируются в `src/components/widgets.tsx` по имени. Оглавление (`modules.ts`) задаёт порядок модулей и уроков, идентификаторы вида `m03-l04`. Урок появляется в «готовых», когда добавлен в `lessons.ts`.

### 5.3 Прогресс и состояние

`src/app/state.ts`: `Progress = { lessons, tasks, predict, quizzes, notes, theme }`. Ключ хранилища `nodejs-textbook:v1`. При изменении структуры данных увеличивай версию и пиши миграцию. Новые поля добавляй с безопасными значениями по умолчанию.

Добавить: `flashcards` (коробки Лейтнера), `interviewHistory` (история мок-интервью), `selfAssessment` (самооценка), `stories` (STAR-истории), `sandboxDrafts` (черновики кода), `sqlLabState` (необязательно).

### 5.4 Шаблон симулятора

Каждый симулятор состоит из трёх частей:

1. **Модель** (`src/engine/<name>.ts`): чистая функция `simulate(scenario) → { frames, log, invariants }`. Тип `Frame` содержит всё, что нужно нарисовать. Детерминирована (при необходимости принимает seed).
2. **Сценарии** (`src/content/<module>/scenarios.ts`): данные; из них же генерируется код лабораторий и эталонные результаты.
3. **Виджет** (`src/components/<Name>Sim.tsx`): рисует кадр, использует `SimPlayer` для управления, показывает разбор (`explanation`), бейдж «модель».

Оракул-тест (`src/engine/<name>.test.ts` и/или `tools/oracle/<name>.ts`) сверяет модель с реальной системой (раздел 11.2).

### 5.5 Песочницы

| Песочница | Реализация | Особенности |
|---|---|---|
| JS (готово) | Web Worker из Blob, подмена `console`, таймаут 3 с, ожидание «осадки» (`settleMs`) | Расширить: тесты-функции (`TestExercise`, см. 8.3), перехват необработанных reject, подмена таймеров для детерминизма |
| TypeScript | `typescript` в ленивом чанке, диагностика по ходу ввода, затем удаление типов и запуск как JS | Тесты типов через `// @ts-expect-error` и вспомогательные типы `Equal`, `Expect` |
| SQL | PGlite в Worker, датасеты как seed-скрипты, сброс одним кликом, вывод таблицы и плана | Ограничение на время запроса; защита от случайных `DROP` не нужна (локальная копия), но кнопка «Сбросить базу» обязательна |
| Мини-Redis | собственная реализация на TS (чистая), виртуальные часы | Покрыть ~40 команд, сверить с реальным Redis оракулом (11.2) |
| Терминал-команды (локальные задания) | не исполняется, только показ и копирование | Это не эмулятор оболочки |

### 5.6 Ленивая загрузка

Каждый «тяжёлый» виджет подключается через динамический `import()`; реестр `widgets` хранит ленивые компоненты (`lazy` + `Suspense`-подобная обёртка). CodeMirror тоже выносится в отдельный чанк. Цель: стартовый JS главной страницы меньше 250 КБ (gzip меньше 90 КБ). Проверяется в CI (бюджет размера).

## 6. Стандарты контента

### 6.1 Шаблон урока

Урок состоит из блоков в таком порядке (разрешены вариации, но все элементы обязательны):

1. **Зачем это знать** (1 абзац: где встречается, почему спрашивают).
2. **Ментальная модель** (определения, таблица или схема; без воды).
3. **Интерактив** (симулятор или песочница; подпись, что делать).
4. **Правила, которые надо знать наизусть** (нумерованный список, 4–8 пунктов).
5. **Типичные ошибки** (3–6 пунктов).
6. **Как спросят / как ответить** (минимум 2 блока `interview`: вопрос + образцовый ответ 4–8 предложений).
7. **Практика** (минимум одна задача `task` с понятным режимом, подсказками, критериями).
8. **Тест** (5–8 вопросов, у каждого объяснение; позиции правильных ответов разные).
9. **Что дальше** (одна строка, ссылка на следующий урок: делается автоматически навигацией).

Объём: 700–1500 слов текста плюс интерактив. Лучше короче и точнее.

### 6.2 Тон и язык

- Обращение на «ты», деловой, без панибратства и без пафоса.
- Русский с английскими терминами там, где так говорят на собеседованиях (event loop, backpressure, consumer group).
- Термин при первом упоминании: русское пояснение рядом с английским.
- Без эмодзи в тексте, кроме значков режимов 🌐 💻 🔀 (значки в заголовках callout подставляет компонент).
- Короткие абзацы, списки только там, где содержание списочное, таблицы для сравнений.
- Образцовые ответы на собеседовании пишутся от первого лица и **честно**: без вымышленного опыта.

### 6.3 Правила достоверности

1. Утверждение о поведении системы проверено запуском (оракул, лаборатория) **или** сверено с официальной документацией (ссылка в `docs/research/mNN.md`).
2. Если версионно-зависимое поведение, указывай версию («с Node 11…») и проверяй.
3. Неподтверждённое помечай в тексте словом «уточнить» и заноси в `docs/open-questions.md`.
4. Не пиши «всегда» и «никогда», пока не убедился. Лучше «как правило» и объяснение исключений.
5. Не копируй текст документации. Пересказ своими словами плюс ссылка.
6. У каждого модуля есть `docs/research/mNN.md`: источники, что проверено запуском, что не подтверждено.

### 6.4 Задачи (`task`)

- Идентификатор `N.M` (модуль.номер), буквенные суффиксы для дополнений (`1.1b`), `L` для локальной части (`1.1L`).
- Обязательные поля: `id`, `title`, `mode`, `summary`. Для локальных: `steps`, `commands` (с пояснениями), `expected`, `check`. Для браузерных упражнений: `exercise` с `expected` и `solution`.
- **Подсказки** выдаются по одной, от наводящей к почти прямой (2–3 штуки).
- **Решение** скрыто до первой попытки.
- Критерий выполнения автоматический, где возможно (вывод совпал, тесты зелёные), иначе чек-лист самопроверки.
- Для 💻 и 🔀 указывай предусловия (версии, порты), команды **с кнопкой копирования** и ожидаемый вывод.

### 6.5 Тесты (`quiz`)

- 5–8 вопросов на урок, один правильный ответ, 3 правдоподобных неверных.
- Позиции правильных ответов распределены (не все «второй вариант»).
- У каждого вопроса объяснение, почему верный верен, и (где уместно) почему популярный неверный не подходит.
- Вопросы проверяют понимание, а не заучивание названий.

### 6.6 Вопросы собеседования

Блоки `interview` из всех уроков автоматически собираются в банк вопросов модуля 14 (раздел 9.15). Поэтому у каждого блока должны быть: формулировка вопроса как её задаёт интервьюер, ответ, и желательно теги (модуль, уровень). См. тип `Block` в приложении A (поле `tags`, добавить).

### 7.4 Мобильные правила

- Симуляторы перестраиваются в одну колонку, тяжёлые панели сворачиваются.

- Для 💻-задач в мобильной версии есть пометка «выполняется на компьютере», а команды всё равно копируются.

### 8.1 Обобщение `PredictGame`

Сейчас игра читает сценарии event loop. Нужно: принимать список «фрагментов» `{ id, title, intro, source, answer: string[], explanation: string[] }`. Эталонный ответ получается реальным запуском на этапе сборки (`tools/record-traces`), а не пишется вручную. Фрагменты хранятся в данных урока. Для event loop остаётся источник `scenarios.ts`.

### 8.2 `Timeline` (общий компонент)

Используется для: изоляции транзакций (две сессии), дедлока, брокеров (продюсер, брокер, консьюмер), Saga, Outbox, graceful shutdown, async-канала ШЭП. Реализовать один раз, SVG, адаптивно.

### 8.3 `TestExercise`

Расширение `Exercise`: вместо сравнения вывода пользователь пишет функцию, а харнесс запускает набор тестов:

```ts
interface TestExercise {
  starter: string;          // например: export function retry(fn, opts) { ... }
  tests: { name: string; code: string }[];   // код теста, использует expect(...) и fake timers
  timeoutMs?: number;
  solution?: string;
}
```

Харнесс: мини-раннер (`describe`, `it`, `expect.toBe/toEqual/toThrow/rejects`) в Worker, подмена `setTimeout` управляемыми часами, отчёт «прошёл/упал» по каждому тесту с сообщением.

**Проект:** «Сервис приёма заявок с отправкой во внешнюю систему».

**Состав:** NestJS, TypeScript, PostgreSQL; Redis (кэш и rate limiting); REST API и WebSocket-уведомления о статусе; асинхронная обработка через брокер (ретраи, DLQ, идемпотентность); Outbox; учебный SOAP-мок «внешней системы» (из `labs/m12/soap-mock`); подпись документа (учебная или через NCANode, если доступен); Docker Compose; тесты; нагрузочный прогон; README с описанием решений.

**Минимальный API:** `POST /applications` (идемпотентный, `Idempotency-Key`), `GET /applications/:id`, `GET /applications?cursor=…` (keyset), `POST /applications/:id/cancel`; WebSocket `/ws` для событий статуса.

**Сущности:** `application`, `outbox`, `inbox`, `status_history`.

**События:** `application.created`, `application.submitted`, `application.accepted`, `application.rejected`, `application.failed`.

#### m13-l01. Дизайн проекта

#### m13-l02. Реализация и презентация
- Этапы с критериями приёмки (чек-лист в уроке): 13.2 ядро (CRUD, миграции, валидация); 13.3 асинхронность (брокер, outbox, ретраи, DLQ); 13.4 интеграция (SOAP-мок и подпись); 13.5 надёжность (кэш, rate limiting, graceful shutdown); 13.6 качество (тесты, нагрузочный тест, README); 13.7 🌐 презентация: рассказ на 3 минуты и на 10 минут (шаблон).

### 9.15 Модуль 14. Подготовка к собеседованию

**Цель:** превратить знания в уверенные ответы. Это самый ценный для пользователя раздел, **его базовые компоненты (MockInterview, Flashcards, STAR) реализуются рано** (фаза C).

#### Компоненты

**MockInterview.**
- Банк вопросов: `src/content/m14/questions.ts`. Структура: `{ id, module, tags[], level: 'junior'|'middle'|'senior', kind: 'hr'|'tech'|'mgmt'|'live'|'design', question, keyPoints[], referenceAnswer, followUps[], rubric: {criterion, weight}[] }`. Значительная часть **автоматически собирается из блоков `interview` всех уроков** (скрипт `tools/build-question-bank.ts`), плюс дополнительные вопросы по каждому модулю. Цель: не менее 150 вопросов к релизу.
- Поток: выбор режима (по модулю, по типу, случайный, «слабые темы»), **один вопрос за раз**, поле для ответа, необязательный таймер; **эталонный ответ скрыт до отправки своего**; самооценка по рубрике (чек-лист ключевых пунктов, итог 1–10); сохранение в `interviewHistory`.
- **Экспорт для разбора в чате с Claude:** кнопка «Скопировать ответы для разбора» формирует текст: вопрос, ответ пользователя, самооценка, и просит оценить по шкале 1–10 с разбором ошибок и примером сильного ответа. (Внутри сайта автоматической оценки ИИ нет.)
- Подсказка «слабые темы» берётся из результатов тестов и самооценок.

**Flashcards.** Коробки Лейтнера (5 коробок, интервалы 1, 2, 4, 8, 16 дней), колоды по модулям, сгенерированные из банка вопросов (лицо: вопрос, оборот: ключевые пункты). Режим «быстрый повтор перед собеседованием».

**STAR-конструктор.** Поля Situation, Task, Action, Result с наводящими вопросами, счётчик слов и таймер 2 минуты, чек-лист «есть ли измеримый результат», сохранение в `stories`, экспорт. Данные из 0.4 и 9.5 предзаполняют историю по выбору. **Не генерируй истории за пользователя.**

**Конструктор рассказа о себе.** Структура на 60–90 секунд: сейчас, прошлое (ключевые проекты), почему эта роль, чем полезен. Три шаблона для «почему Middle после Senior/Lead» (честные формулировки; пользователь выбирает и правит). Счётчик времени чтения вслух.

#### m14-l01. Рассказ о себе и ответ «почему Middle»
- Конструктор рассказа, шаблоны, чек-лист ошибок (слишком длинно, перечисление технологий без результатов, оправдания).
- Практика: 14.1, 14.2 🌐.

#### m14-l02. Истории STAR
- Минимум 4 истории: оптимизация, инцидент, архитектурное решение, конфликт или ревью. Привязка историй к вопросам вида «расскажи о случае, когда…».
- Практика: 14.3 🌐, 14.4 🌐 заготовки честных ответов по слабым местам (NestJS, брокеры, ШЭП, Kalkan).

#### m14-l03. Live coding и system design
- **Live coding:** 20 типовых заданий с тестами в браузерной песочнице: async-утилиты (`retry`, `pLimit`, `debounce`, `memoize`), работа со streams (подсчёт строк, трансформация), SQL (оконные функции, агрегаты, поиск дублей), мини-API; разбор подхода «думай вслух».
- **System design:** чек-лист этапов (требования, оценки, API, модель данных, компоненты, масштабирование, отказы, компромиссы); 3–4 тренировочные задачи (сокращатель ссылок, очередь уведомлений, лента заявок с интеграцией во внешнюю систему, rate limiter как сервис); доска на `DiagramCanvas`.
- Практика: 14.6 🌐, 14.7 🌐.

#### m14-l04. Зарплата и вопросы работодателю
- Шаблон исследования зарплатной вилки (поля для данных, которые пользователь собирает сам; **не вписывай рыночные цифры без источника**), скрипт ответа на вопрос о зарплате, позиция на торге; список из 8–10 вопросов работодателю (стек, процесс код-ревью, оценка и планирование, дежурства, тестовые контуры интеграций, развитие, адаптация).
- Практика: 14.8, 14.9 🌐.

#### m14-l05. Мок-интервью

## 11. Качество, тесты, проверка достоверности

### 11.1 Уровни проверок

| Уровень | Что проверяет | Инструмент |
|---|---|---|
| Unit движков | чистая логика моделей | `vitest` |
| Оракул-тесты | модель против реальной системы | `vitest` + docker (CI) |
| Линтер контента | целостность и полнота уроков | `tools/lint-content.ts` |
| e2e в браузере | сценарии пользователя, ошибки консоли, мобильная вёрстка | `puppeteer-core` + Chrome |
| a11y | нарушения доступности | `@axe-core/puppeteer` |
| Бюджет размера | размер стартового бандла и чанков | скрипт в CI |
| Лаборатории | `starter` падает, `solution` проходит | CI |

### 11.2 Оракул-тесты (обязательный подход)

Для каждого симулятора с реальным аналогом:

1. Сценарии описаны данными (`scenarios.ts`).
2. Из сценария генерируется программа для реальной системы (Node-скрипт, SQL-сессии, команды Redis, действия с брокером).
3. Тест запускает её (в CI через docker) и сравнивает с моделью.
4. Для недетерминированных систем сравниваются **инварианты** (список в описании сценария), а не точные трассы.
5. Сценарии, где реальное поведение зависит от машины, помечаются `deterministic: false` и показывают предупреждение.

Примеры: event loop (готово); изоляция транзакций (две сессии PostgreSQL, ожидаемые результаты по шагам); мини-Redis (последовательности команд, ответы совпадают с реальным Redis); RabbitMQ и Kafka (инварианты доставки).

### 11.3 Линтер контента (`npm run lint:content`)

Проверки (ошибка блокирует CI):
- идентификаторы уроков, задач, тестов уникальны и соответствуют `modules.ts`;
- у каждого готового урока есть: минимум один `widget` или `sandbox`-задача, минимум два блока `interview`, один `quiz` не менее чем из 5 вопросов, минимум одна `task`;
- у каждого вопроса теста есть `explain`, индекс `answer` валиден, позиции правильных ответов в тесте не одинаковы;
- у каждой `task`: `mode`, `summary`; для `local` и `hybrid`: `commands`, `expected`; для `exercise`: `expected`, не менее 2 подсказок;
- нет `TODO`, `lorem`, заглушек, строк «уточнить» без записи в `docs/open-questions.md` (предупреждение);
- ссылки на лаборатории (`labs/...`) существуют;
- каждый `widget` из реестра существует.

### 11.4 Доступность и вёрстка

В e2e: прогон axe на главной, странице модуля, готовом уроке, песочнице (ошибки уровня serious и critical блокируют); проверка отсутствия горизонтального скролла на ширинах 360, 390, 768; проверка тёмной темы.

### 11.5 Определение готовности

**Урок готов**, если: проходит линтер; есть интерактив и практика; все факты подтверждены (раздел 6.3) и источники записаны в `docs/research/mNN.md`; симуляторы покрыты оракулом или явно помечены как «модель без оракула» с причиной; локальные лаборатории проходят `starter`/`solution`; e2e и a11y зелёные; ручной просмотр на ширине 390 px выполнен.

**Модуль готов**, если готовы все его уроки, есть сводный тест модуля (10–15 вопросов, необязательный), обновлён банк вопросов модуля 14, обновлён `README`.

## 12. CI/CD, ветки, коммиты

### 12.1 Ветки и pull request'ы

- `main` всегда зелёный и собирается.
- Одна функция или один модуль = одна ветка `feat/mNN-название` и один PR. Небольшие PR лучше больших.
- В описании PR: что сделано, какие факты проверены и как, скриншоты ключевых виджетов (десктоп и телефон), чек-лист готовности из 11.5.

### 12.2 Коммиты

Сообщения на русском, в повелительной или нейтральной форме: «Добавить симулятор Kafka», «Исправить порядок фаз в модели». Не смешивай в одном коммите контент и движок без необходимости.

### 12.3 GitHub Actions

Рабочие процессы:
1. **ci**: `npm ci`, `tsc --noEmit`, `npm test`, `npm run lint:content`, `npm run build`, `npm run build:single`, проверка размера, e2e (Chrome), axe.
2. **oracle** (по расписанию и при изменении движков): поднимает сервисы через docker, запускает оракул-тесты и лаборатории (`starter` падает, `solution` проходит).
3. **pages** (по желанию): публикация `dist/` в GitHub Pages из `main`. Не включать, пока пользователь не попросит (репозиторий приватный; Pages для приватных репозиториев зависит от тарифа).
4. **release**: сборки `dist-single`, `dist-offline` прикрепляются к тегу релиза.

### 12.4 Определение готовности релиза

Релиз `v1.0`: все 15 модулей готовы; нет блокирующих замечаний a11y; банк вопросов не менее 150 с рубриками; в каждой лаборатории `solution` проходит; `docs/open-questions.md` пуст или содержит только осознанно оставленные пункты; в README описана установка и запуск трёх режимов (`dist`, `dist-single`, `dist-offline`).

### Приложение A. Контракты данных (снимок из репозитория)

```ts
// src/content/types.ts
export type Mode = 'browser' | 'local' | 'hybrid';

export interface Exercise {
  starter: string;
  expected: string[];     // ожидаемый вывод console.log построчно
  settleMs?: number;      // сколько ждать асинхронные колбэки
  solution?: string;
}

export interface CommandItem { cmd: string; note?: string }

export interface Task {
  id: string;
  title: string;
  mode: Mode;
  summary: string;
  steps?: string[];
  commands?: CommandItem[];
  expected?: string;
  hints?: string[];
  check?: string[];       // пункты самопроверки
  widget?: { name: string; props?: Record<string, unknown> };
  exercise?: Exercise;
}

export interface QuizQuestion { q: string; options: string[]; answer: number; explain: string }

export type Block =
  | { t: 'md'; text: string }
  | { t: 'callout'; kind: 'info' | 'warn' | 'tip'; title?: string; text: string }
  | { t: 'interview'; q: string; a: string }
  | { t: 'widget'; name: string; props?: Record<string, unknown>; caption?: string; model?: boolean }
  | { t: 'quiz'; id: string; title?: string; questions: QuizQuestion[] }
  | { t: 'task'; task: Task };

export interface Lesson { id: string; blocks: Block[] }
export interface LessonRef { id: string; title: string; summary?: string }
export interface Module {
  id: string; num: number; title: string; summary: string;
  priority: 'critical' | 'high' | 'medium' | 'base';
  lessons: LessonRef[];
}
```

**Планируемые расширения:**
- `Block.interview`: `tags?: string[]`, `level?: 'junior' | 'middle' | 'senior'`, `kind?: 'hr' | 'tech' | 'mgmt' | 'live' | 'design'`, `keyPoints?: string[]`.
- `Block.md`: `detail?: boolean` (скрывается в режиме «Коротко»).
- `Task`: `testExercise?: TestExercise` (8.3), `prerequisites?: string[]`, `labPath?: string`.
- `Progress`: `flashcards`, `interviewHistory`, `selfAssessment`, `stories`, `sandboxDrafts`, `viewMode`.
